# GPT-6 Astra 升级了，你的 Codex 还在用旧规则？

<div class="course-meta"><span>更新：2026-09-08</span><span>完整教程</span><span>19 个项目实测</span></div>

**需要直接复制？** [打开完整提示词与全量修改版](astra-agents-skills-prompts.md)，或[下载教程和提示词 ZIP](../../downloads/astra-agents-skills/astra-agents-skills-complete-kit.zip)。页面提供单项目试用与全量正式修改两种完整用法。

**GPT-6 Astra 发布后，Codex 用户值得先做一件事：重新检查自己的 AGENTS.md 和 Skills。**

模型更能遵循指令，也会更认真地执行你留下的旧要求。过去为了催它读文档、跑测试、先问清楚而补上的规则，现在可能带来多余的步骤，甚至让任务提前停住。

**以前帮你管住 AI 的规则，现在可能限制了新模型的发挥。**

OpenAI 的官方指南明确建议检查模型可读取的 Skills、AGENTS.md 等指令文件。Eric Provencher 也专门写了《Rethinking skills and prompts for GPT-6 Astra》，拆解哪些要求应该重新审视，以及怎样调整 Skills、AGENTS.md 和任务提示。[OpenAI 指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra) · [Eric 原文](https://x.com/pvncher/status/2095991462416490862)

下面用一个例子贯穿讲解：**假设你已经装了一份叫 `article-writer` 的 Skill，负责公众号文章的起草、检查和发布。** 它把“先问清需求、读取素材、写正文、检查封面、准备发布”写成一套固定流程。现在你只让 Codex 改一个标题，它却又开始提问、读整套资料，甚至检查起了封面。

接下来，我们就整理这份现有 Skill，以及影响它的 AGENTS.md：起草时读写作要求，检查时读相关清单，已经要求发布时再进入发布流程；只改标题，就完成这次标题修改。

前半篇使用这个假设例子解释方法，后半篇展示我实际运行后的产物和删减数据。完整提示词也会一起给出，方便你处理自己的项目。

## 01｜先分清：全局、项目、Skills 与运行记录，各放一层

AGENTS.md 是给 AI 的工作约定；Skill 是某一类任务的专门说明。在这个例子里，项目 AGENTS.md 可以告诉 Codex 本项目的文章素材放在哪里，`article-writer` 则说明怎样起草、检查和发布文章。

**全局 AGENTS.md，在 Codex 界面里对应哪里？** 打开桌面端的“设置 → 个性化”，找到 **Codex 说明（自定义指令）**。这个区域编辑的是个人级 AGENTS.md，默认文件位置是 `~/.codex/AGENTS.md`，用于跨项目的习惯和约定。[官方设置说明](https://learn.chatgpt.com/docs/reference/settings#personalization) · [全局 AGENTS.md 说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md#create-global-guidance)

项目 AGENTS.md 则放在具体项目文件夹中。例如，一份公众号项目的 AGENTS.md 可以记录这批文章的素材目录和专有用词。这些项目事实无需都填进“个性化”。

整理之前，先把信息放对位置。

| 信息 | 更适合放在哪里 | 例子 |
|---|---|---|
| 多个项目都适用的沟通习惯、协作约定 | 全局 AGENTS.md；在界面中通过“设置 → 个性化”里的“Codex 说明”编辑 | 默认中文回答；专业词要解释并举例 |
| 当前项目的事实、特殊操作、限制和资料位置 | 当前项目或相关子目录的 AGENTS.md | 这个公众号项目的素材目录、专有用词 |
| 某一类任务才需要的方法或工具用法 | 对应 Skill 的 `SKILL.md` | `article-writer` 如何根据任务选择写作、检查或发布流程 |
| 很长的步骤、例子、参考资料 | Skill 的 `references`，用于存放按需读取的资料 | `references/drafting.md` 存写作要求；`references/publishing.md` 存发布步骤 |
| 可以反复自动完成的固定操作 | Skill 的 `scripts`，用于存放可执行脚本 | `scripts/check_cover.py` 自动检查封面图片尺寸 |
| 本次目标、输入、交付要求和完成条件 | 你在当前 Codex 对话里发送的任务提示词 | 把两份资料合成一篇面向新手的文章，核对并保存 |
| 已确认的决定、原因、进度和待办 | 项目工作记录或交接文件 | 已采用哪版标题、为什么采用、下一步补什么 |

这样，长期规则负责反复需要的约定，具体资料在用到时再读，今天的进度也有单独的位置。

沿用文章 Skill 的例子，这三句话可以分别这样放：

- **“默认用中文回答”**：写进全局 AGENTS.md，也就是“个性化”里的“Codex 说明”，以后换项目也能沿用。
- **“本次文章面向新手”**：直接写在这次 Codex 对话的任务消息中，例如“请根据这两份资料写一篇文章，读者是第一次使用 Codex 的人”。
- **“发布前检查封面尺寸”**：写进 `article-writer` 的 `references/publishing.md`，让 Codex 准备发布时读取。

这里的“当前任务”，指你在当前 Codex 对话（session）里交代的这次工作。对话是你持续沟通的位置；“这次文章面向谁、交付什么”，是你在其中写下的具体要求。

“发布说明”在这个例子中就是 `references/publishing.md`，是一份供 AI 阅读的 Markdown 文件，里面可以写“检查封面尺寸、确认摘要、核对发布账号”等步骤。如果已经有程序能自动检查图片尺寸，这段可执行代码才放在 `scripts/check_cover.py`，再由发布说明指向它。上面的文件名是结构示例，实际使用时应核对相应文件确实存在。

这样，只改正文中的一句话时，就不必读取整份发布说明或运行封面检查程序。

同一条重要规则，尽量只维护一份正文，其他入口指向它。否则，一处已经更新，另一处还留着旧要求，AI 就可能读到两套说法。

如果项目已经使用多个 AI 助手，它们各自负责什么，可以放在相应的助手配置中。容易变化的模型设置、当前进度，也不必永久写在全局规则里。

最后，让 Codex 核对实际使用的是哪些文件。电脑上存在一个文件、本次读过一次、以后会自动采用，是三种不同情况，不能混为一谈。

## 02｜Skills：先改入口，再改正文

这里的“入口”指 Skill 的 `name` 和 `description`。在我们的例子里，`name` 就是 `article-writer`；`description` 则要写清什么时候需要它，例如起草完整文章，或明确要求执行文章检查、发布流程时。

AI 先根据这些信息选择 Skill，再阅读 `SKILL.md` 中的方法和步骤。`SKILL.md` 是每个 Skill 的核心说明文件，例如它可以写明一篇文章需要哪些输入、交付什么结果。

先解决选得对不对，再解决选中之后怎么做。

**它到底提供了什么额外帮助？**

先看这份 Skill 是否提供了模型无法自行得知的内容：专门工具的用法、项目特殊要求、稳定的输出格式，或者经过实际使用检验的方法。

例如，“默认把资料保存到指定目录”有明确作用；“认真思考、努力完成”如果没有补充任何信息，就可以考虑缩短。

不要因为一份说明以前给旧模型用过，就认定它现在完全无效。要看它是否仍然解决你的实际问题。

**只改标题，为什么也会启动整套写作流程？**

先检查 `description` 是不是写得太宽。

`description` 应当把“什么时候使用”说准确。安装的 Skills 很多、`description` 又很长时，Codex 还可能缩短模型能看到的内容，反而让它难以选准。

可以这样改：

| 原来的 `description` | 改写后的 `description` |
|---|---|
| 所有写作任务都使用，开始前先访谈用户 | 起草完整公众号文章，或明确要求执行文章专项检查、发布流程时使用；仅改标题或错字时不用 |

长背景、完整步骤和能力介绍，放进 `SKILL.md` 正文或 `references`。例如，“起草所需信息不足时补充询问”可以写在写作分支中，不必让每种任务都先进入访谈。`description` 先回答清楚：什么时候需要我？

改完后，用“从零写一篇文章”和“只改一个标题”分别试一次，看看 AI 是否真的选对。只把 `description` 写短，还不足以说明问题已经解决。

**几份 Skill 会不会同时要求“先用我”？**

把相关 Skills 的 `description` 放到一起看。

一份要求所有任务先规划，另一份要求所有任务先访谈，还有一份要求改完必须再启动另一轮检查。叠加起来，小任务也可能被拉成长流程。

应让它们各自负责清楚的事情。例如，写完整文章和检查引用是两项不同工作；一项任务可能需要两者，但不用每次都把两套方法全部启动。

`SKILL.md` 中的要求也要一起核对。不能只把 `description` 里的“必须”改成“建议”，正文仍然保留一整串互相冲突的步骤。

**这套方法，能不能只在需要时使用？**

对于步骤太多的 Skill，可以选择三种处理方式：

- 缩小适用范围。例如，只有从零写文章且信息不足时才提问，改标题时不用。
- 保留方法，但只在你点名要求时使用。例如，你说“先采访我，了解写作需求”时，才进入访谈。
- 如果它持续打断工作，也没有值得保留的内容，就先不用这套说明。

方法的使用方式可以改变，不需要把写作、检查、调试等能力一并放弃。

还要检查有没有附带操作。例如，检查文章前要求配置其他工具，或文章写完后自动发布。这些都要依据当前任务判断，不能因为某份说明把它们连在一起，就默认每次都做。

暂停使用是否真正实现，也要按工具支持的方式核对。只改 `name` 或文件名，不能直接宣布它已经不再被使用。

**`SKILL.md` 能不能先指路，详细步骤需要时再读？**

我们的 `article-writer` 包含写作、检查、发布三种工作，可以在 `SKILL.md` 中先对应到具体文件：

| 用户这次要求做什么 | `SKILL.md` 指向哪里 |
|---|---|
| 从零起草完整文章 | `references/drafting.md`，存放写作要求 |
| 专门检查文章的事实、引用或格式 | `references/reviewing.md`，存放对应检查清单 |
| 已明确要求发布文章 | `references/publishing.md`，存放发布步骤和相关操作要求 |

这样，AI 当前只写正文，就不用先把所有发布步骤读一遍。

长步骤和参考资料放在 `references`，需要自动执行的操作可以放在 `scripts`。例如，发布说明可以在需要检查封面时调用 `scripts/check_cover.py`；检查清单可以在需要核对链接时调用 `scripts/check_links.py`。这些仍是结构示例，实际引用的文件必须存在。小而单一的 Skill 可以继续放在一个文件里，不必为了整理而拆出一堆空目录。

**为什么 `SKILL.md` 改了，AI 还是照旧执行？**

因为旧要求可能还在 `references` 或 `scripts` 里。

例如，你从 `SKILL.md` 删掉了“每次检查整个项目”，但它仍让 AI 读取 `references` 中的检查清单。清单里留着同样的话，AI 读完后，还是会照做。

所以，要沿着 `SKILL.md` 的引用检查 `references` 和 `scripts`，看 AI 会继续读什么、执行什么。移动文件后，核对路径正确、文件可用，里面的要求也已经同步调整。

**哪些先后顺序必须保留，哪些可以放开？**

先取得完整资料，再比较异同，这种先后关系必须保留。没有原文，就谈不上准确比较。

但“无论做什么，都先问十个问题，再写计划，再等一次确认”，就需要检查是否每次都必要。

可以把固定步骤改成具体条件：缺少会影响结果的信息时才提问；资料齐全、目标清楚时，就选择合适的方法继续完成。

如果同一套 Skills 还供同事或不同模型使用，要保留他们共同需要的要求。例如，发布时使用哪个账号、图片存放在哪里，不能因为换了模型就删掉。

**`skill-creator` 是什么，它自己更新了吗？**

Codex 确实有 OpenAI 随产品提供的系统内置 `skill-creator`。它的用途是帮助创建或修改 Skill：把你想完成的工作整理成合适的 `name`、`description`、`SKILL.md`，再按实际需要组织补充资料或脚本。可以在 Codex 中用 `$skill-creator` 调用它。[官方 Skill 创建说明](https://learn.chatgpt.com/docs/build-skills#create-a-skill)

例如，你可以说：

> 请使用 Codex 系统内置的 skill-creator，整理现有的 article-writer。保留写作、检查和发布的方法，让它按本次任务读取对应资料；只改标题时不进入整套流程。请先核对实际使用的 skill-creator 来自哪里。

之所以要确认来源，是因为同名 Skill 可能来自不同地方。系统内置版本与自行安装的版本，不能只看 `name` 就当成同一份。

**官方指导有过更新。** Eric 在这篇介绍 GPT-6 Astra 的文章中明确提到，他们近期更新了 `skill-creator` 的指导，重点包括更短且准确的 `description`、按需读取资料，以及减少不必要的固定步骤。[Eric 原文的 Skill files 部分](https://x.com/pvncher/status/2095991462416490862)

**本次全量整理使用了系统版的检查脚本，没有修改 `skill-creator` 本身。** 下文统计的是实际改写或迁移的私有 Skills。使用工具生成或调整文件之后，仍要检查 `description` 是否准确、步骤是否适量、`references` 和 `scripts` 是否有效。

## 03｜AGENTS.md：留下长期有用的要求，改掉过宽的规定

Skills 解决专项任务怎么做，AGENTS.md 则会持续影响它适用范围内的工作。

逐条检查时，可以采用四种处理方式：

| 处理 | 适用情况 | 例子 |
|---|---|---|
| 保留 | AI 无法猜出的事实、明确习惯和真实边界 | 素材目录、默认中文、不要覆盖已有修改 |
| 删除 | 已过时，或没有额外作用的重复提醒 | 失效路径、已经不再使用的旧流程 |
| 改写 | 本意有用，但范围太宽或容易误解 | 把“每次读所有资料”改成按任务查对应文件 |
| 移动 | 只在特定项目或任务中需要 | 把发布清单移到发布说明，把进度移到工作记录 |

对于要移动的内容，先安排好真实可用的新位置。没有反复使用价值的旧案例，也不必全部换个地方继续堆着。

具体修改时，重点看下面几件事。

**文档从“每次全读”改成“需要时查”。**

核对价格时查价格表，修改程序的数据结构时查对应说明，准备发布时查发布清单。让 AI 根据任务补充阅读其他必要资料，不必用规则强制它每次全读。

入口本身也要更新。文件是否存在，操作方式是否变化，都要核对。程序项目还可以对照当前安装配置、实际脚本及自动检查设置，确认旧说明里的命令仍然适用。

**检查写清楚“查什么”，也写清楚“什么时候够了”。**

改标题，核对文字和保存结果即可；修复程序问题，就需要检查原来的问题是否解决、相关功能是否受影响。

项目必做检查仍然保留。检查通过以后，只有新改动、新失败或尚未解决的具体疑点，才扩大或重复检查。同一份内容和同一环境下，已有的有效结果可以复用；相关状态变化后，再重查受影响部分。

**把可以连续完成的工作说清楚。**

如果已经交代“整理资料、写成文章、核对并保存”，就应把这些做到结束，不默认在第一稿后停下来。

程序项目也可以写明具体情况：本地检查只使用临时数据、不连接正式服务时，在已经授权的修复范围内，可以连续检查、修复本次引起的问题、再检查，无需每一步重新询问。

涉及其他范围的操作，仍然按实际授权处理。例如，完成本地文章，并不自动包含对外发布。

**你自己的稳定习惯，可以留下。**

“默认用中文回答”“必须使用专业词时先解释并举例”，都可以是长期约定。

有人希望直接拿结果，有人希望顺便理解关键思路。让规则服务你的使用习惯，不必为了减少几行，把这些也删掉。

**如果需要整理结构，可以按六方面组织。**

沟通习惯、要求的适用关系、执行方式、检查方式、工具与协作、正式资料位置。内容少时合并写即可，不强制凑齐六个标题。

其中，要求之间如何协调，应遵循工具和平台的实际规则；并行工作，也就是让多个助手同时处理任务，只适合真正独立的工作。例如，可以分别阅读两份材料，但同一篇最终稿应统一改写，避免互相覆盖。

如果某条规则导致任务停住，让 AI 说明具体是哪份文件、哪句话，以及它为什么认为必须停。这样才知道要修正的是规则，还是它对规则的理解。

本次任务的完成标准则放在当前提示词里。例如：

> 把这两份资料整理成一篇面向新手的文章，核对事实与链接，保存到指定目录。交付文章及仍未核实的问题，完成后结束，不自行发布。

## 04｜这八类 Skills，值得重点检查

不需要因为模型升级就把所有 Skills 重做。先看以下类别里，是否存在对应问题。

| 类型 | 重点检查什么 | 调整方向 |
|---|---|---|
| 网页与电脑操作 | 是否大量重复模型已经能完成的基础操作；是否遗漏账号与环境要求 | 减少无用步骤，保留账号、专用浏览器环境、工具参数和下载位置 |
| 程序检查 | 是否只有通用提醒，缺少项目实际会犯的错误 | 保留特殊约定和真实错误案例，用已知有问题的例子检查效果 |
| 长文档处理 | 分段是为了容量，还是为了读齐资料和定位出处 | 容量条件变化后重新判断；图片文字、附件、视频文字稿仍要取得完整 |
| 数据分析 | 是否限制了有价值的复杂任务，或缺少计算口径 | 按实际需要扩展，保留单位、口径与核对方法，用已知答案检查 |
| 多步骤任务 | 是否把普通操作顺序写得过死 | 保留必须先完成的业务条件，让 AI 选择适合本次任务的做法 |

## 08｜看结果时，重点核对这四件事

**第一，整理的范围是不是你要求的范围。**

**第二，它删掉的是什么，留下的是什么。**

这次有一份 Skill，原来的 `SKILL.md` 有 498 行，新版是 27 行。重复内容合并后，详细方法放进了三份 `references` 文件，主说明留下适用条件、关键约定和资料入口。

其他修改主要集中在四个范围：

- **资料读取**：根据本次任务查相关内容，减少无条件全文预读。
- **检查要求**：检查范围与实际改动对应，避免一个小修改默认检查整个项目。
- **任务衔接**：复用已经明确的要求和仍然有效的决定，减少重复提问与停顿。
- **内容位置**：把阶段进度和历史记录移出长期规则，补齐缺失资料并修复失效引用。
